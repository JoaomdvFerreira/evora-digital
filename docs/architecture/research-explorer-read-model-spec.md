# Open Évora Research Explorer — Read-Model Specification

**Status:** RE-00 spike specification, validated against the real corpus. Authoritative for RE-01 implementation.
**Relates to:** `docs/architecture/ADR-001-research-explorer-architecture.md`

This is the only contract the Explorer UI may depend on. All files are generated by the RE-01 adapter from `research/` via `tools/validate-research.js#validateResearchTree()`; none are hand-edited or canonical.

## Source of truth for shape

Node types = schema `prefix` values discovered under `research/schemas/*.schema.json` (currently `SRC-`, `EVD-`, `PRB-`, `ASM-`, `HYP-`). Edge types = each schema's own `references` array. No node/edge shape is hardcoded per record type in the adapter; adding a new schema file with a `references` array is sufficient for it to appear correctly, per Track C.

## `manifest.json`

```json
{
  "readModelVersion": "1.0.0",
  "generated_at": "2026-08-12T00:00:00.000Z",
  "generator": "apps/research-explorer/scripts/build-data.js",
  "source_commit": "<git rev-parse HEAD, if available>",
  "totalRecords": 220,
  "counts": { "SRC-": 89, "EVD-": 111, "PRB-": 10, "ASM-": 10, "HYP-": 0 },
  "schemaPrefixes": ["SRC-", "EVD-", "PRB-", "ASM-", "HYP-"]
}
```
Purpose: lets the UI show a corpus-freshness banner and detect a stale/regenerate-needed state without parsing anything else.

`readModelVersion` versions **this read-model contract** (the manifest/index/edges/record-detail shapes on this page), not the canonical research schemas. The two evolve independently: `Canonical Research schema vN → Adapter → Explorer Read Model vM`. A canonical schema change (new field, new enum value, new schema file) does not require bumping `readModelVersion` unless it changes what this document says the generated files' own shape is; the adapter simply re-derives new node/edge/summary content under the same read-model contract. `readModelVersion` only bumps when this spec document itself changes (e.g. a new top-level manifest field the UI must start handling, or a change to how `record-detail` files are addressed). The UI reads `readModelVersion` to detect a read model built by an incompatible adapter version, independent of any canonical schema question.

## `index.json`

Flat array, one entry per record, summary fields only (never full record bodies — those live in per-record detail files, per the scalability envelope in ADR-001 D7):

```json
[
  {
    "id": "PRB-0005",
    "type": "PRB-",
    "label": "Traffic/parking vs pedestrian quality",
    "file": "research/problems/PRB-0005.yaml",
    "summaryFields": {
      "domain": "mobility",
      "validation_status": "...",
      "status": "..."
    }
  }
]
```
`label` uses the D2 fallback-field convention. `summaryFields` is a small, schema-specific but non-exhaustive set of enum/status fields useful for filtering (exact set decided per schema in RE-01; not part of this contract's stability guarantee — `id`, `type`, `label`, `file` are).

## `edges.json`

Flat array, one entry per resolved reference (not per declared field — a list-valued field with 3 targets produces 3 edges):

```json
[
  { "from": "EVD-000105", "to": "SRC-0092", "field": "source.source_id", "required": false },
  { "from": "PRB-0005", "to": "EVD-000022", "field": "evidence", "required": false }
]
```
Unresolved reference targets never appear here — `validateResearchTree()` already fails the build (via `tools/validate-research.js`'s own error list) if a reference points at a nonexistent ID, so `edges.json` is guaranteed internally consistent with `index.json`'s id set at generation time.

## `record-detail/<ID>.json`

One file per record, full canonical content plus provenance and resolved links:

```json
{
  "id": "PRB-0005",
  "type": "PRB-",
  "file": "research/problems/PRB-0005.yaml",
  "record": { "...": "full parsed record as validated" },
  "outgoingEdges": [{ "field": "evidence", "to": "EVD-000022" }],
  "incomingEdges": [{ "from": "ASM-0005", "field": "problem" }]
}
```
`incomingEdges` is derived (reverse index over `edges.json`) so the UI never has to compute it client-side per click.

## Guarantees

- **Deterministic:** identical `research/` content always produces byte-identical generated output (stable key ordering, no timestamps embedded except `manifest.json`'s own `generated_at`/`source_commit`).
- **Fails closed:** if `validateResearchTree()` returns any `errors`, the build step exits non-zero and writes nothing — a broken/inconsistent read model is never published.
- **No semantic inference:** the adapter does not compute similarity, ranking, clustering, or any derived judgment beyond what `references` arrays and summary fields already state.
- **Provenance retained:** every node in `index.json`/`record-detail` carries its exact source YAML path (`file`), so "trace evidence" (RE-03) can always point back to the canonical file.
